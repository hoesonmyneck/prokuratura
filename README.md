# Инновационная система мониторинга

Веб-карта коридора реконструкции автодороги «Западный регион»
(Бейнеу — Саксаульск — Улгайсын — Кызылорда): трасса, ход строительства
и кадастровые участки вдоль неё.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # production-сборка в dist/
```

## Стек

- **Vite + React + TypeScript**
- **MapLibre GL JS** — рендер карты, без API-ключей и лицензионных ограничений
- Подложки: CARTO Light, OpenStreetMap, Esri World Imagery (спутник)

## Состояние данных

| Что | Источник | Статус |
| --- | --- | --- |
| Кадастровые участки | ЕГКН, map.gov4c.kz | **реальные**, 5 996 шт. в полосе ±1 км |
| Границы областей и районов | ЕГКН, слои `egkn:regions`, `egkn:districts` | **реальные**, упрощены до 150 м |
| Ось «Кызылорда — Саксаульск» | ведомость углов поворота, 98 ВУ | **реальная**, сходится с ведомостью до метра |
| Ось двух других плеч | [src/data/road-segments.json](src/data/road-segments.json) | схематичная, ждём координаты |
| Населённые пункты | [src/data/road.ts](src/data/road.ts) | по общедоступным координатам |

Два плеча из трёх по-прежнему нарисованы на глаз, и это стоит держать в голове:
на «Бейнеу — Саксаульск» схематичная линия даёт 528 км против 800 по документации.
Поэтому протяжённость трассы по областям нигде не считается и не показывается.

Проект кончается на КМ 462, в 35 км не доходя до посёлка Саксаульский, а два
схематичных плеча упирались прямо в посёлок — на карте зиял разрыв. Настоящую
ось не трогаем, хвосты схематичных сводит к её концу
[join-schematic.mjs](scripts/join-schematic.mjs). Смещение разносится
по последним 150 км, иначе на стыке появился бы излом, читаемый как поворот
трассы; сейчас там 0,1° и 0,6°. Скрипт идемпотентен.

Насколько это важно, показала замена оси на плече Кызылорда — Саксаульск: число
участков в полосе упало с 17 174 до 5 996, причём по г. Кызылорда — с 8 484 до 16.
Нарисованная линия заходила в город, а проект начинается обходом на км 24+900,
в 17,5 км от центра. Восемь с половиной тысяч участков числились в коридоре
по ошибке рисунка.

Карта зафиксирована в границах проекта (`PROJECT_BOUNDS` в [src/config/map.ts](src/config/map.ts)) —
за пределы региона выйти нельзя.

## Кадастр: как устроена выгрузка

Публичная кадастровая карта ЕГКН работает на GeoServer, слой `egkn:u_view` доступен
по WFS. Три особенности источника:

1. Слой — параметризованное SQL-представление. Без `viewparams=district_id:<id>`
   возвращает ноль объектов. Поэтому выгружать можно **только по одному району за раз**,
   область или всю страну — нельзя.
2. Координаты приходят в родной UTM-зоне района (EPSG:32640 / 32641). Серверное
   перепроецирование не работает — у слоя не объявлен SRID, `srsName` игнорируется.
3. CORS не настроен, из браузера дёргать нельзя.

Из-за этого данные готовятся заранее скриптом:

```bash
node scripts/fetch-cadastre.mjs             # полоса ±1 км (по умолчанию)
node scripts/fetch-cadastre.mjs --km 3      # шире полоса
```

Скрипт обходит 12 районов вдоль трассы ([scripts/districts.json](scripts/districts.json)),
пересчитывает геометрию в WGS-84, отбирает участки в заданной полосе от оси дороги
и пишет `public/cadastre.geojson`. Ось берётся из того же
[road-segments.json](src/data/road-segments.json), что и на карте, — когда придут
точные координаты трассы, достаточно поправить его и перезапустить скрипт.

`scripts/gov4c-chain.pem` — недостающие промежуточные сертификаты: сервер ЕГКН
отдаёт неполную цепочку, и без них node не может установить TLS-соединение.
Проверка сертификата при этом не отключается.

### Объём

Полоса задаёт размер файла — выбирать по потребности. Текущая выгрузка:

| Полоса | Участков | Размер |
| --- | --- | --- |
| **±1 км** | **6 004** | **4.5 МБ** |

Файл лежит в public/ под неизменным именем и кешируется на сутки
(см. `vercel.json`), поэтому после деплоя браузеры отдавали бы прежние участки.
Адрес версионируется меткой сборки — `cadastre.geojson?v=<хеш коммита>`,
она подставляется через `define` в [vite.config.ts](vite.config.ts). Длинный
кеш сохраняется, но новая сборка обнуляет его сразу.

Прежние замеры для ±0.5, ±2 и ±3 км сюда не переношу: они сделаны против
схематичной оси и после её замены на плече Кызылорда — Саксаульск ничего
не значат. Понадобится другая ширина — прогнать скрипт и посмотреть.

Если понадобится вся ширина районов целиком (≈198 000 участков, ~300 МБ), GeoJSON
в браузер грузить нельзя — нужны векторные тайлы или серверная отдача по bbox.

### Категории земель

Цвет участка — по коду категории. Подписи даны только для кодов, которые
подтверждаются самими данными (01 — крестьянские хозяйства, 02 — жилые дома,
03 — газопровод и объекты ж/д). Коды 04–07 встречаются единицами и сведены
в «прочие», чтобы не приписывать им названия наугад.

## Административные границы

Трасса идёт через три области и 12 районов; на карте показаны настоящие контуры
из ЕГКН — слои `egkn:regions` и `egkn:districts`. В отличие от `u_view` это
обычные слои: отдаются без `viewparams`, фильтруются через CQL и приходят
в EPSG:3857.

```bash
node scripts/fetch-boundaries.mjs                  # допуск упрощения 150 м
node scripts/fetch-boundaries.mjs --tolerance 500  # грубее и легче
```

| Файл | Объектов | Точек | Размер |
| --- | --- | --- | --- |
| [src/data/regions.json](src/data/regions.json) | 3 | 20 475 → 2 282 | 45 КБ |
| [src/data/districts.json](src/data/districts.json) | 12 | 16 831 → 2 673 | 54 КБ |

Контуры ужимаются Дугласом — Пекером. Вместе это ~100 КБ, поэтому файлы лежат
в `src/` и попадают в бандл — в отличие от кадастра, ради них отдельная сетевая
загрузка не нужна.

Районы берутся ровно те, из которых выгружался кадастр
([scripts/districts.json](scripts/districts.json)), — один список на обе выгрузки.
Полное деление трёх областей (51 район) не тянем: к коридору оно отношения
не имеет и весит втрое больше.

Две особенности, из-за которых код выглядит именно так:

1. **`egkn:districts` отдаёт дубликаты.** У Бейнеуского района три записи
   с разной геометрией, у Аральского — две. По атрибутам их не различить:
   `is_del` везде `false`, отметок времени нет, а `change_id` обманывает —
   у неверной записи Аральского он как раз больше.

   Арбитр — граница области: внешний край района обязан лежать на ней. Скрипт
   берёт вершины, идущие вдоль областной границы, и сравнивает медиану
   отклонения: у верного Аральского это 1 м, у устаревшего — 1 632 м. Если
   записи ложатся на границу одинаково (случай Бейнеуского), побеждает более
   подробный контур.

   Цена ошибки здесь видна на глаз: пока выбирался устаревший контур,
   граница Аральского с Казалинским расходилась на 1,1 км и на карте двоилась.
   После исправления расхождение 66 м — меньше допуска упрощения.
2. **Подписи расставляются по-разному на двух уровнях.** Район подписывается
   на середине проходящей по нему трассы — так подпись оказывается там, куда
   смотрят. Для трёх районов, мимо которых схематичная ось прошла стороной
   (г. Шалкар, Айтекебийский, г. Казалинск), берётся центроид.

   Названия областей длинные и висят на карте всегда, поэтому для них ищется
   самое пустое место внутри контура: перебор по сетке максимизирует расстояние
   сразу до трассы, населённых пунктов, собственной границы области и края
   видимого кадра. Центроид не годится — у Мангистауской и Актюбинской областей
   он лежит далеко за кадром проекта.

   Найденный оптимум не всегда удачен на глаз: у Мангистауской и Кызылординской
   он приходится на верх контура, где подпись липнет к трассе. Для них в списке
   `REGIONS` стоит `labelPrefer: 'south'` — из мест, где запас не хуже 60 %
   от лучшего, берётся самое южное.

На карте уровни различаются рисунком: область — толстый цветной пунктир, район —
тонкая сплошная тёмная линия со светлой подложкой (чтобы не тонуть в спутнике).
Границы рисуются поверх кадастровых участков: под 17 тысячами полигонов линию
было бы не видно. Оба уровня включены по умолчанию, выключаются в панели слоёв;
подписи районов появляются с зума 6, иначе на общем плане они сливаются
с названиями областей.

## Ось трассы из ведомости углов поворота

Плечо «Кызылорда — Саксаульск» построено по настоящей геодезии. Исходник —
«Сокр.план КС-2 с ВУ», листы 1–3: ведомость углов поворота, прямых и кривых.

**Ведомость в PDF лежит картинкой** (JPEG внутри чертежа), поэтому цифры
не копируются ничем — это не защита и не настройки просмотрщика. Данные
перенесены вручную в [axis-kyzylorda-saksaulsk.json](src/data/axis-kyzylorda-saksaulsk.json):
98 вершин с координатами, радиусами и переходными кривыми.

```bash
node scripts/verify-axis.mjs   # проверить перенос
node scripts/build-axis.mjs    # построить ось и записать в road-segments.json
```

### Почему переносу можно верить

Ведомость избыточна: углы, пикетаж и элементы кривых обязаны воспроизводиться
из одних только координат и радиусов. [verify-axis.mjs](scripts/verify-axis.mjs)
считает всё заново и сверяет.

| Проверка | Результат |
| --- | --- |
| Углы поворота, 98 шт. | худшее расхождение 0,5″ |
| Пикетаж каждой вершины | худшее расхождение 0,20 м |
| Полная длина | 462 484,86 м против 462 484,81 м по ведомости |
| Замыкание кривых при построении | 6 мм |

Проверка не декоративная: она поймала две ошибки переноса — угол на ВУ62
(9°26'42" вместо 9°25'42") и разряд в координате ВУ67 (415363 вместо 415353),
из-за которого пикетаж уезжал на 4,2 м до конца трассы.

Сторона поворота в данных **не хранится**: она однозначно следует из координат,
а два узких столбца «влево»/«вправо» на растровой ведомости читаются
ненадёжно — из 98 строк я перепутал 24. Не надо держать в данных то, что
нельзя проверить и можно вычислить.

### Обозначения проекта

Ведомость в чертежах лежит картинкой, а сам чертёж — векторный, с живым
текстовым слоем. В нём подписаны площадки отдыха, транспортные развязки,
переходы ЛЭП и границы очередей, и у каждой подписи есть пикетаж вида
«КМ 30+058». Этого достаточно, чтобы поставить обозначение точно: **пикетаж
откладывается вдоль оси, привязка чертежа к местности не нужна вовсе.**
Значит, точность обозначений равна точности оси, а не аккуратности рисунка.

```bash
pip install pymupdf pillow numpy scipy
python scripts/extract-features.py   # снять подписи с пикетажем
python scripts/extract-symbols.py    # найти знаки на растре листов
node scripts/build-features.mjs      # разложить по оси и по привязке
python scripts/extract-icons.py      # вырезать условные знаки из легенды
```

| Тип | Объектов | Откуда положение | Знак |
| --- | --- | --- | --- |
| Скотопрогон или проезд сельхозтехники | 28 | с рисунка | есть |
| Переход земляного полотна | 26 | пикетаж | нет в легенде |
| Площадка отдыха | 17 | пикетаж | есть |
| АЗС и сервисы | 10 | с рисунка | есть |
| Транспортная развязка | 5 | пикетаж | есть |
| Граница очереди строительства | 3 | пикетаж | нет в легенде |

Пикетажем на чертеже подписаны не все объекты. Мосты, проезды сельхозтехники,
скотопрогоны, АЗС, скважины, ДЭУ и ДЭП нарисованы только значками. У ДЭУ и ДЭП
подписи есть («ДЭУ 56 км1646»), но это километраж **существующей** дороги,
а не проектный, и без таблицы соответствия он на нашу ось не ложится.

Мостов в выборке нет намеренно: на самом плане их значок вырождается в синий
квадрат 36×36, неотличимый от других синих меток вдоль трассы. Скотопрогон
и проезд сельхозтехники — один и тот же кружок, различаются только рисунком
внутри; сверка с образцом их не разводит (корреляции 0,46 против 0,41),
поэтому они сведены в один тип. Выдумывать, где корова, а где трактор, хуже,
чем назвать честно.

Тип определяется по **ближайшему** ключевому слову, а не по набору слов вокруг.
Сначала было по набору — и это дало неверный ответ: подписи на чертеже наложены
плотно, слово от соседнего объекта попадало в набор, и «переход земляного
полотна» записывался в переходы ЛЭП. Переходов ЛЭП в выборке нет вовсе:
названия линий («АО КЕГОК ВЛ 220 кВ») на чертеже подписаны, но собственного
пикетажа у пересечения нет — рядом всегда стоит отметка другого объекта.

Якорь разбора — слово «КМ»: оно стоит только у подписей объектов, а точки
кривых (НКК, ККК, НПК, КПК) подписаны пикетами без него и в выборку
не попадают. Листы перекрываются, поэтому дедупликация по паре
(тип, пикетаж). Из 74 отметок на чертежах вышло 49 объектов: подписи
размечают границы, и близкие отметки одного типа собираются в один объект
(площадка отдыха — две границы с разбегом 1.8–2.2 км, развязка — несколько
отметок в пределах пары километров).

### Объекты без пикетажа: привязка листа

Что нарисовано только значком, берётся с самого листа. Знаки залиты чистыми
цветами, которых на топооснове не бывает, — по ним собираются пятна нужного
размера и формы, а тип уточняется сверкой с образцом из легенды.

Лист привязывается к местности по подписям «КМ n+mmm»: их положение известно
и на листе, и на местности (через ось). Простой МНК тут не работает — на листах
есть врезки с увеличенными фрагментами и подписи стыков, стоящие у края,
а не на своём месте; такие точки уводят решение на километры. Поэтому RANSAC
([lib/georef.mjs](scripts/lib/georef.mjs)): подобие задаётся парой точек,
перебираются все пары, побеждает та, с которой согласуется больше остальных.

| Лист | Точек | Невязка привязки |
| --- | --- | --- |
| 1 | 45 из 46 | медиана 37 м, 90 % 185 м |
| 2 | 30 из 40 | медиана 50 м, 90 % 105 м |
| 3 | 39 из 39 | медиана 47 м, 90 % 110 м |

Все три листа дали один масштаб — 70,5 м на единицу страницы. Это независимая
проверка: серия рисована в одном масштабе, и привязки об этом «не знали».

Две поправки, без которых ничего не сходилось:

1. **Растр и текстовый слой живут в разных системах.** Растр рисуется
   в повёрнутой системе страницы, `get_text` отдаёт неповёрнутую. У листов 1 и 2
   поворот 270°, и знаки уезжали от контрольных точек на десятки километров.
2. **Знак вынесен в сторону от дороги на выноске** — его центр стоит
   в километрах от трассы. Все эти объекты придорожные, поэтому знак сажается
   на ось: поперечное смещение уходит целиком.

Насколько это точно, проверяется само: площадки отдыха известны обоими
способами. Расхождение — медиана 1,2 км, и оно в основном от того, что знак
отмечает одну точку внутри двухкилометровой площадки, а пикетаж даёт её
середину. **Такие объекты могут быть смещены вдоль трассы примерно на километр.**
Для карты мониторинга этого достаточно: значок показывает, что объект здесь
есть, а не где именно стоит колонка. В интерфейсе они ничем не помечены
намеренно — точность нужна плану дороги, а не условным объектам.

### Условные знаки

Знаки на карте — те же, что на чертеже: `extract-icons.py` режет их прямо
из блока «Условные обозначения» на листе 1, делает белый фон прозрачным
и кладёт в квадрат ([src/assets/icon-*.png](src/assets/)). Рисовать свои
нельзя — читающий план и читающий карту видели бы разные знаки.

В легенде есть развязки и площадки отдыха. **Перехода ЛЭП и границы очереди
в ней нет**, поэтому на карте они остаются нейтральными кружками: придумать
условный знак, которого в проекте не существует, хуже, чем показать точку.

Иконки живут в стиле карты, а смена подложки стиль пересоздаёт — поэтому
`ensureIcons` добавляет их заново на каждый `styledata`, как и слои.

### Система координат

Определена перебором: поперечная Меркатора, осевой меридиан 63°, ложный восток
500 000. Остальные варианты промахиваются на сотни километров. Датум и масштабный
коэффициент подтвердить нечем — взят СК-42, **остаточная неопределённость
порядка 100–250 м**. Подтверждение: ось проходит в 1,6–8 км от Жосалы, Аксуата,
Камыстыбаса и Аральска, то есть по своему коридору.

Кривые строятся численно: клотоида, дуга, клотоида. Контроль — конец каждой
кривой обязан лечь на исходящий тангенс вершины.

## Ход строительства

В панели есть блок «Ход строительства»: у каждого участка поле, куда вписываются
построенные километры. Введённое сразу видно и на карте — построенная часть
рисуется сплошной линией в полную силу, оставшаяся пунктиром и вполсилы.

Цветом ход стройки не кодируется: цвет уже занят технической категорией участка,
второй смысл на него не навесить. Пунктир против сплошной линии — обычная
картографическая условность для «пока не построено».

**Километры отсчитываются от паспортной длины, а не от нарисованной оси.**
Ось схематична и короче паспорта, поэтому доля считается от паспорта, а на карте
эта же доля откладывается вдоль линии:

| Участок | Паспорт | Геометрия оси | 30 км это | На карте отложится |
| --- | --- | --- | --- | --- |
| «Бейнеу — Саксаульск» | 800 км | 528 км | 3,75 % | 19,8 км линии |
| «Улгайсын — Саксаульск» | 312 км | 251 км | 9,62 % | 24,2 км линии |
| «Кызылорда — Саксаульск» | 462 км | 447 км | 6,49 % | 29,0 км линии |

Откладывай скрипт 30 км прямо по геометрии, на бейнеуском плече вышло бы 5,7 %
вместо 3,75 % — прогресс был бы завышен в полтора раза.

### Где хранятся значения

Состояние общее: его держит [api/progress.ts](api/progress.ts) — функция
на Vercel поверх Redis. Отметил километры один человек, увидели все.

[src/data/road-progress.json](src/data/road-progress.json) остался значением
по умолчанию: им карта живёт, пока не пришёл ответ, и на него откатывается,
если хранилище не настроено.

Обновления соседей подтягиваются опросом раз в 20 секунд и при возврате
на вкладку. Веб-сокет ради трёх чисел, меняющихся раз в неделю, не нужен.
Ввод отправляется с паузой в 0,6 с после последнего нажатия — иначе набор
«300» ушёл бы тремя запросами, и последним мог оказаться промежуточный «30».

### Локальная разработка

`npm run dev` про Vercel ничего не знает: запрос к `/api/progress` попадал бы
в обычную раздачу файлов, и клиент получал исходник функции вместо JSON.
Поэтому тот же контракт в деве обслуживает middleware из
[vite.config.ts](vite.config.ts), а состояние лежит в `.progress-dev.json`
(в `.gitignore`). Правила проверки чисел повторяют серверные, справочники
читаются из тех же JSON.

Ни Vercel CLI, ни Redis для локальной работы не нужны. Сбросить локальное
состояние — удалить `.progress-dev.json`.

### Подключение хранилища

1. В проекте на Vercel: **Storage → Create Database → Redis**.
2. Привязать store к проекту (**Connect Project**) — переменные подставятся сами.
3. **Передеплоить.** Переменные окружения применяются только к новым деплоям,
   поэтому уже работающая функция про свежий store не узнает.

Функция принимает любой из двух способов доступа и выбирает первый доступный:

| Способ | Переменные | Как работает |
| --- | --- | --- |
| REST | `UPSTASH_REDIS_REST_URL` + `..._TOKEN`, либо `KV_REST_API_*` | HTTP, без рукопожатия |
| TCP | `REDIS_URL` или `KV_URL` | соединение на время запроса |

**Почему рантайм Node, а не Edge.** Изначально это была Edge-функция с REST-клиентом
Upstash. Но Redis-хранилище Vercel отдаёт только `REDIS_URL` — обычный адрес
`rediss://`, а по TCP Edge ходить не умеет в принципе. На Node работают оба способа,
и подключённого store хватает без ручной настройки переменных.

Если хранилища нет, `GET` отвечает `200` со значениями из файла и полем
`problem`, где написано, чего именно не хватает (только имена переменных,
никогда значения). Тот же текст видно в панели. `PUT` в этом случае честно
отвечает `503`.

### Кто может менять

**По умолчанию менять может любой посетитель.** Так карта работает сразу после
деплоя, без настройки, но для карты надзорного органа это стоит закрыть:

1. Добавить переменную окружения `PROGRESS_WRITE_TOKEN` с произвольным
   секретом.
2. Оператору один раз открыть карту ссылкой `?token=<секрет>`. Ключ ляжет
   в его браузер, а из адресной строки сразу уберётся, чтобы не разошёлся
   по скриншотам.

У всех остальных поля станут нередактируемыми, а `PUT` вернёт `403`.
