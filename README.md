# Карта а/д «Западный регион»

Веб-карта коридора реконструкции автодороги (Бейнеу — Саксаульск — Улгайсын — Кызылорда)
с трассой и кадастровыми участками вдоль неё.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # production-сборка в dist/
```

## Стек

- **Vite + React + TypeScript**
- **MapLibre GL JS** — рендер карты, без API-ключей и лицензионных ограничений
- Подложки: CARTO Light, OpenStreetMap, Esri World Imagery (спутник)

## Состояние данных

| Что | Источник | Статус |
| --- | --- | --- |
| Кадастровые участки | ЕГКН, map.gov4c.kz | **реальные**, 17 174 шт. в полосе ±1 км |
| Границы областей и районов | ЕГКН, слои `egkn:regions`, `egkn:districts` | **реальные**, упрощены до 150 м |
| Ось трассы | [src/data/road-segments.json](src/data/road-segments.json) | схематичная, ждём точные координаты |
| Населённые пункты | [src/data/road.ts](src/data/road.ts) | по общедоступным координатам |

Схематичность оси стоит держать в голове: её геометрическая длина 1 226 км против
1 574 км по документации, а на «Бейнеу — Саксаульск» — 528 против 800. Поэтому
протяжённость трассы по областям нигде не считается и не показывается.

Карта зафиксирована в границах проекта (`PROJECT_BOUNDS` в [src/config/map.ts](src/config/map.ts)) —
за пределы региона выйти нельзя.

## Кадастр: как устроена выгрузка

Публичная кадастровая карта ЕГКН работает на GeoServer, слой `egkn:u_view` доступен
по WFS. Три особенности источника:

1. Слой — параметризованное SQL-представление. Без `viewparams=district_id:<id>`
   возвращает ноль объектов. Поэтому выгружать можно **только по одному району за раз**,
   область или всю страну — нельзя.
2. Координаты приходят в родной UTM-зоне района (EPSG:32640 / 32641). Серверное
   перепроецирование не работает — у слоя не объявлен SRID, `srsName` игнорируется.
3. CORS не настроен, из браузера дёргать нельзя.

Из-за этого данные готовятся заранее скриптом:

```bash
node scripts/fetch-cadastre.mjs             # полоса ±1 км (по умолчанию)
node scripts/fetch-cadastre.mjs --km 3      # шире полоса
```

Скрипт обходит 12 районов вдоль трассы ([scripts/districts.json](scripts/districts.json)),
пересчитывает геометрию в WGS-84, отбирает участки в заданной полосе от оси дороги
и пишет `public/cadastre.geojson`. Ось берётся из того же
[road-segments.json](src/data/road-segments.json), что и на карте, — когда придут
точные координаты трассы, достаточно поправить его и перезапустить скрипт.

`scripts/gov4c-chain.pem` — недостающие промежуточные сертификаты: сервер ЕГКН
отдаёт неполную цепочку, и без них node не может установить TLS-соединение.
Проверка сертификата при этом не отключается.

### Объём

Полоса задаёт размер файла — выбирать по потребности:

| Полоса | Участков | Размер |
| --- | --- | --- |
| ±0.5 км | 8 659 | 4.9 МБ |
| **±1 км** | **17 174** | **11.8 МБ** |
| ±2 км | 36 875 | 21 МБ |
| ±3 км | 52 714 | 30 МБ |

Если понадобится вся ширина районов целиком (≈198 000 участков, ~300 МБ), GeoJSON
в браузер грузить нельзя — нужны векторные тайлы или серверная отдача по bbox.

### Категории земель

Цвет участка — по коду категории. Подписи даны только для кодов, которые
подтверждаются самими данными (01 — крестьянские хозяйства, 02 — жилые дома,
03 — газопровод и объекты ж/д). Коды 04–07 встречаются единицами и сведены
в «прочие», чтобы не приписывать им названия наугад.

## Административные границы

Трасса идёт через три области и 12 районов; на карте показаны настоящие контуры
из ЕГКН — слои `egkn:regions` и `egkn:districts`. В отличие от `u_view` это
обычные слои: отдаются без `viewparams`, фильтруются через CQL и приходят
в EPSG:3857.

```bash
node scripts/fetch-boundaries.mjs                  # допуск упрощения 150 м
node scripts/fetch-boundaries.mjs --tolerance 500  # грубее и легче
```

| Файл | Объектов | Точек | Размер |
| --- | --- | --- | --- |
| [src/data/regions.json](src/data/regions.json) | 3 | 20 475 → 2 282 | 45 КБ |
| [src/data/districts.json](src/data/districts.json) | 12 | 16 831 → 2 673 | 54 КБ |

Контуры ужимаются Дугласом — Пекером. Вместе это ~100 КБ, поэтому файлы лежат
в `src/` и попадают в бандл — в отличие от кадастра, ради них отдельная сетевая
загрузка не нужна.

Районы берутся ровно те, из которых выгружался кадастр
([scripts/districts.json](scripts/districts.json)), — один список на обе выгрузки.
Полное деление трёх областей (51 район) не тянем: к коридору оно отношения
не имеет и весит втрое больше.

Две особенности, из-за которых код выглядит именно так:

1. **`egkn:districts` отдаёт дубликаты.** У Бейнеуского района три записи
   с разной геометрией, у Аральского — две. По атрибутам их не различить:
   `is_del` везде `false`, отметок времени нет, а `change_id` обманывает —
   у неверной записи Аральского он как раз больше.

   Арбитр — граница области: внешний край района обязан лежать на ней. Скрипт
   берёт вершины, идущие вдоль областной границы, и сравнивает медиану
   отклонения: у верного Аральского это 1 м, у устаревшего — 1 632 м. Если
   записи ложатся на границу одинаково (случай Бейнеуского), побеждает более
   подробный контур.

   Цена ошибки здесь видна на глаз: пока выбирался устаревший контур,
   граница Аральского с Казалинским расходилась на 1,1 км и на карте двоилась.
   После исправления расхождение 66 м — меньше допуска упрощения.
2. **Подписи расставляются по-разному на двух уровнях.** Район подписывается
   на середине проходящей по нему трассы — так подпись оказывается там, куда
   смотрят. Для трёх районов, мимо которых схематичная ось прошла стороной
   (г. Шалкар, Айтекебийский, г. Казалинск), берётся центроид.

   Названия областей длинные и висят на карте всегда, поэтому для них ищется
   самое пустое место внутри контура: перебор по сетке максимизирует расстояние
   сразу до трассы, населённых пунктов, собственной границы области и края
   видимого кадра. Центроид не годится — у Мангистауской и Актюбинской областей
   он лежит далеко за кадром проекта.

   Найденный оптимум не всегда удачен на глаз: у Мангистауской и Кызылординской
   он приходится на верх контура, где подпись липнет к трассе. Для них в списке
   `REGIONS` стоит `labelPrefer: 'south'` — из мест, где запас не хуже 60 %
   от лучшего, берётся самое южное.

На карте уровни различаются рисунком: область — толстый цветной пунктир, район —
тонкая сплошная тёмная линия со светлой подложкой (чтобы не тонуть в спутнике).
Границы рисуются поверх кадастровых участков: под 17 тысячами полигонов линию
было бы не видно. Оба уровня включены по умолчанию, выключаются в панели слоёв;
подписи районов появляются с зума 6, иначе на общем плане они сливаются
с названиями областей.

## Ход строительства

В панели есть блок «Ход строительства»: у каждого участка поле, куда вписываются
построенные километры. Введённое сразу видно и на карте — построенная часть
рисуется сплошной линией в полную силу, оставшаяся пунктиром и вполсилы.

Цветом ход стройки не кодируется: цвет уже занят технической категорией участка,
второй смысл на него не навесить. Пунктир против сплошной линии — обычная
картографическая условность для «пока не построено».

**Километры отсчитываются от паспортной длины, а не от нарисованной оси.**
Ось схематична и короче паспорта, поэтому доля считается от паспорта, а на карте
эта же доля откладывается вдоль линии:

| Участок | Паспорт | Геометрия оси | 30 км это | На карте отложится |
| --- | --- | --- | --- | --- |
| «Бейнеу — Саксаульск» | 800 км | 528 км | 3,75 % | 19,8 км линии |
| «Улгайсын — Саксаульск» | 312 км | 251 км | 9,62 % | 24,2 км линии |
| «Кызылорда — Саксаульск» | 462 км | 447 км | 6,49 % | 29,0 км линии |

Откладывай скрипт 30 км прямо по геометрии, на бейнеуском плече вышло бы 5,7 %
вместо 3,75 % — прогресс был бы завышен в полтора раза.

### Где хранятся значения

Состояние общее: его держит [api/progress.ts](api/progress.ts) — Edge-функция
на Vercel поверх Redis. Отметил километры один человек, увидели все.

[src/data/road-progress.json](src/data/road-progress.json) остался значением
по умолчанию: им карта живёт, пока не пришёл ответ, и на него откатывается,
если хранилище не настроено.

Обновления соседей подтягиваются опросом раз в 20 секунд и при возврате
на вкладку. Веб-сокет ради трёх чисел, меняющихся раз в неделю, не нужен.
Ввод отправляется с паузой в 0,6 с после последнего нажатия — иначе набор
«300» ушёл бы тремя запросами, и последним мог оказаться промежуточный «30».

### Локальная разработка

`npm run dev` про Vercel ничего не знает: запрос к `/api/progress` попадал бы
в обычную раздачу файлов, и клиент получал исходник функции вместо JSON.
Поэтому тот же контракт в деве обслуживает middleware из
[vite.config.ts](vite.config.ts), а состояние лежит в `.progress-dev.json`
(в `.gitignore`). Правила проверки чисел повторяют серверные, справочники
читаются из тех же JSON.

Ни Vercel CLI, ни Redis для локальной работы не нужны. Сбросить локальное
состояние — удалить `.progress-dev.json`.

### Подключение хранилища

1. В проекте на Vercel: **Storage → Create Database → Redis (Upstash)**.
2. Привязать store к проекту. Переменные окружения (`UPSTASH_REDIS_REST_URL`
   и `UPSTASH_REDIS_REST_TOKEN`, в части конфигураций `KV_REST_API_*`)
   подставляются сами; функция читает оба варианта имён.
3. Передеплоить.

Без переменных функция отвечает `503`, а карта показывает цифры из файла.

### Кто может менять

**По умолчанию менять может любой посетитель.** Так карта работает сразу после
деплоя, без настройки, но для карты надзорного органа это стоит закрыть:

1. Добавить переменную окружения `PROGRESS_WRITE_TOKEN` с произвольным
   секретом.
2. Оператору один раз открыть карту ссылкой `?token=<секрет>`. Ключ ляжет
   в его браузер, а из адресной строки сразу уберётся, чтобы не разошёлся
   по скриншотам.

У всех остальных поля станут нередактируемыми, а `PUT` вернёт `403`.
